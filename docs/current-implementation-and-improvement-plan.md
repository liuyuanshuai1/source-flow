# 当前实现与改进方案

本文件说明公开代码的工作方式和下一步计划。个人订阅清单、浏览器凭据、采集数据库、原始内容、日报及自动任务配置均留在本地，不随仓库发布。

## 当前实现

- `sourceflow.collector` 是 X、小红书和 B 站的入口。Python 进程调用 BrowserAct，控制已配置的 Chrome 会话，执行页面导航和 `scripts/` 中的页内提取脚本。
- X 从账号主页和回复页读取可见帖子；小红书从作者主页读取笔记列表、再打开新笔记详情；B 站从 UP 主主页发现视频，在视频页复用播放器已生成的签名请求获取可用字幕。
- `sourceflow.db` 把来源、内容、来源游标和部分已检查对象写入本地 SQLite。运行结果保存为各平台 JSON、`new_items.json` 和 `run.json`；摘要阶段由外部任务读取结果。
- GitHub Trending 采集不在本仓库采集器的默认运行范围内。仓库保留一个与来源采集分开的 OpenRadar 演示应用。

## 已知边界

1. X 有默认滚动上限，小红书列表提取器只读取初始状态的前 20 条，B 站只读取当前可见列表。当前 `success` 不代表已经覆盖到上次检查的位置。
2. 采集器以来源最新入库时间过滤候选。较早发布但后来才可见的条目可能被漏掉。
3. 部分详情提取失败会留下不完整正文或跳过对象；当前缺少通用的待重试队列。无字幕视频不会定期自动复查。
4. `new_items.json` 来自采集候选，而非数据库确认新增的行；同一天再次运行可能覆写同名运行文件。

## 改进顺序

1. 每来源记录 `complete`、`partial`、`failed`、检查范围和停止原因。只有接上上次完整覆盖的位置才推进覆盖检查点；触及页数上限标记为 `partial`。
2. 先记录发现的稳定 ID，再获取详情或字幕。失败项进入待重试队列，后续运行先补欠账。
3. 由数据库写入操作返回实际新增或更新的 ID，据此生成 `new_items.json`。每次运行使用唯一 ID 保存审计文件。
4. 逐来源验证 API 获取方式。已验证的来源可选 API；其他来源保留 Chrome 路径。不要预建自动获取 Cookie、自动改代码和多层回退框架。
5. 用置顶或乱序内容、页数上限、单条详情失败及重复运行等样本验证不漏采、不重复、结果数量一致。

调度频率和订阅清单由使用者在本机设置；公开仓库不提供实际运行环境的配置。
